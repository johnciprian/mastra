Remediation plan · companion to the auth swappability audit

Getting all five seams to A−, without touching EE

A fork-owned Apache-2.0 auth kit that owns identity, the capability descriptor, sessions and conformance — then four phases wiring the Factory to it. Every EE-licensed dependency is reimplemented, never ported.

4 phases ~3.5–4 weeks, one engineer 8 kit modules each phase has a hard exit gate

The EE boundary, stated precisely

Your constraint is the load-bearing design input, so it gets pinned down first. The good news: all eight capability interfaces already live outside ee/ under Apache-2.0, and mastracode/ today contains zero EE references. There is a clean line to draw — it just runs through an unexpected place.

One import decides everything

@mastra/core/auth is not safe: its barrel reaches @internal/auth, whose src/index.ts:373 does export * from './ee', and packages/core/src/auth/ee/index.ts opens with a side-effecting import './telemetry'. Importing it executes EE code. @mastra/core/server is safe: packages/core/src/server/auth.ts re-exports the eight interfaces and eight guards by explicit name, and EE appears only as erased import type in types.ts:7–9.

  • Allowed@mastra/core/server — the contract, the guards, registerApiRoute. Runtime-clean.
  • AllowedErased type references reaching EE declarations through MastraServerConfig — zero bytes shipped, per your ruling.
  • Forbidden@mastra/core/auth, @mastra/core/auth/ee, @internal/auth/ee, EEUser, buildCapabilities, and the shipped CookieSessionProvider — Apache itself, but only reachable through the tainted barrel.
  • ForbiddenPorting ee/capabilities.ts. We derive our descriptor from the Apache interfaces instead. Same idea, independently written, no licence gate.
  • Flagpackages/server/src/server/fga-permissions.ts:31 does a module-scope import * as authEE from '@mastra/core/auth/ee'. That is pre-existing platform behavior on the /api/* path, not something this plan adds — but it is the one place EE runs at runtime today, and worth a deliberate look from whoever owns the licence question.

Enforcement, not intention: the kit ships an ESLint no-restricted-imports rule plus a CI test that walks the kit’s resolved module graph and fails on any specifier containing /ee. The boundary becomes a build error, not a code-review habit.

What A− means for each seam

Exit criteria, not aspirations. Each is checkable, and each is gated in a phase below.

Seam Grade What has to be true
Contract design B+→A− Identity is declared, not sniffed — a real AuthIdentity with a required id, plus an overridable toIdentity(). Cookie name, state format and the PKCE read side all move from convention into the contract. Kit is semver’d with a written stability policy.
Backend seam B−→A− The Factory imports only the kit. instanceof MastraAuthWorkos and the WORKOS_* reach-through are deleted and @mastra/auth-workos leaves the dependency list. RouteAuth becomes the only identity path. Org-lessness stops 403ing. Logout revokes, and is POST.
UI seam D+→A− Sign-in renders from the descriptor. A CI test greps factory-ui for provider-name literals and fails on any hit. The credentials form posts to a descriptor-supplied endpoint. An unknown provider renders correctly, with correct labelling.
Testability B−→A− A runnable describeAuthProvider() conformance suite that every shipped provider executes in its own CI. Host tests cover a cookie-only request through the gate and every capability branch. Provider-selection tests drop from 60 s boots to the existing config-capture seam.
Documentation D→A− A capability reference table (interface → routes unlocked → methods required), a start-to-finish “write a Factory auth provider” guide, and the four undocumented obligations promoted to documented contract. Every doc example type-checks in CI.

The kit

mastracode/auth-kit, publishing as @mastra/factory-auth — sited in your own area rather than the shared packages/ tree so upstream merges stay cheap. Apache-2.0, eight modules, no EE anywhere in its graph. (@mastra/auth is already taken by an unrelated Apache JWT helper package; name is yours to settle.)

contract.ts

One import site

Re-exports the eight interfaces and eight guards from @mastra/core/server. Provider authors import one thing; if upstream drifts, one file changes.

Contract · enforces the EE boundary
identity.ts

Declared identity

AuthIdentity with a required id, and toAuthIdentity() handling id, uid, sub and {session, user}. Providers override via an optional toIdentity(). Replaces both the shape-sniffer and EEUser.

Contract · backend · unbreaks Firebase
capabilities.ts

Our capability descriptor

describeAuth(provider) → sign-in kind, labels, sign-up state, feature flags — derived purely from the Apache guards. Independently written; no licence gate, no RBAC, no telemetry.

UI seam · replaces ee/capabilities.ts
organizations.ts

Orgs for providers without them

withSyntheticOrganizations() gives any provider a valid IOrganizationsProvider, plus a host-side resolveTenant() so org-lessness degrades instead of 403ing.

Backend · unblocks Cognito, Supabase, Firebase
session.ts

The host owns the cookie

HMAC-signed session cookie over node:crypto, with one declared name. Written fresh because the shipped equivalent is only reachable through the EE-barrelled entry point.

Contract · backend
state.ts

One state format

Shared encodeState / decodeState, so the Factory and packages/server stop disagreeing about whether handleCallback receives the raw value or the UUID half.

Contract · unbreaks Okta
testing/

Composable fakes

fakeProvider() with capability mixins, so a host test can conjure “SSO but no orgs” in one line and never stub an env var.

Testability
conformance/

Proof, not inspection

describeAuthProvider(factory) — a drop-in suite a provider package runs in its own CI to prove it satisfies the contract, including the four obligations.

Testability · docs

Four phases

Ordered so each phase leaves the tree shippable, and so the riskiest reversal — the identity change — lands behind a conformance suite rather than in front of one.

Phase 1

Kit foundation

~1 week

Pure addition. Nothing consumes the kit yet, so nothing can regress — and the EE boundary gets its enforcement before any code depends on it.

Scaffold the package and lock the boundary
Apache-2.0 header, tsdown build matching the sibling packages, the ESLint restricted-imports rule, and the CI module-graph test that fails on any /ee specifier. Write this test first — it is the constraint made executable.
mastracode/auth-kit/{package.json, tsdown.config.ts, eslint.config.js, src/__tests__/no-ee.test.ts}
Write contract, identity, state, session
The four primitives everything else builds on. identity is the one to get right: a required id, an escape hatch for providers whose token shape you cannot change, and no vendor field anywhere in the type.
src/{contract,identity,state,session}.ts
Write capabilities and organizations
Derive the descriptor from the guards, from scratch. Keep it deliberately smaller than the EE version — sign-in shape and feature booleans only. RBAC and FGA are explicitly out of scope and stay that way.
src/{capabilities,organizations}.ts
Write the fakes and the conformance suite
Both are deliverables, not test scaffolding. The conformance suite doubles as the executable specification the docs phase points at.
src/testing/, src/conformance/
Exit gate
  • The no-EE module-graph test passes and is proven — add a temporary EE import, watch CI go red, revert.
  • The conformance suite runs green against a fake provider and red against a deliberately broken one.
  • Kit builds and type-checks standalone, with nothing else in the repo importing it yet.
Phase 2

Backend seam

~1 week

The behavioural phase. Everything here is observable through HTTP, so every change lands with a test that drives a real request.

Replace the shape-sniffer with the kit
Delete toFactoryAuthUser and FactoryAuthUser.workosId; route every identity read through toAuthIdentity. This is the change that makes a Firebase-shaped or raw-JWT-shaped provider stop authenticating as nobody.
mastracode/factory/src/auth.ts:41–43, :190–231
Cut the WorkOS coupling out of the neutral module
Remove isWorkOSAuth, getWorkOSProvider, envFallbackAuthProvider and the static import; drop @mastra/auth-workos from the Factory’s dependencies. The audit confirmed this path has no production callers — its real cost is a vendor package in the graph and a forced vi.mock in two suites.
mastracode/factory/src/auth.ts:1, :161–179, :325, :334 · package.json:58
Close the two identity back doors
Migrate the three modules that bypass RouteAuth and read the request context directly, so the port becomes the single path rather than the preferred one.
workspace.ts:13 · rules/binding-context.ts:4 · integrations/github/session-subscriptions.ts:5
Make org-lessness survivable
Generalize the user:${userId} fallback that already exists in the credentials path so the seven org-gated route groups degrade instead of 403ing, and the workspace layer stops throwing.
routes/provider-credentials.ts:74–75 → kit resolveTenant() · workspace.ts:316
Fix logout, and adopt one state format
Call destroySession on the SSO path, move logout to POST (a GET logout is CSRF-triggerable by any <img>), and switch both callback paths to the kit’s state codec. Audit the five providers whose destroySession body is empty.
mastracode/factory/src/auth.ts:434, :569, :603
Exit gate
  • A test drives a cookie-only request through the gate and gets an authenticated identity — the browser path, finally covered.
  • A fake provider returning { uid } authenticates successfully end to end.
  • A fake provider with no organizations capability reaches the board without a 403.
  • grep -r "workos" mastracode/factory/src returns nothing outside changelogs.
Phase 3

UI seam

~3 days

The smallest phase and the biggest grade jump — D+ to A− — because the deficit is one decision made in one place.

Emit the descriptor from /auth/me
Replace the bare provider.name payload with the kit’s descriptor. The handler already evaluates a capability guard one line earlier; it just throws the answer away.
mastracode/factory/src/auth.ts:400–424
Render from capability, not from name
Branch on descriptor.signIn.kind. Keep the name check as a labelled legacy fallback for one release, then delete it. An unknown provider gets a correct generic hosted-login button instead of a GitHub logo.
factory-ui/src/ui/pages/SignInPage.tsx:154–157, :225
Un-hardcode the credentials endpoint
The form currently posts to better-auth’s wire format. Take the path from the descriptor so any IAuthHttpHandler provider — including the Firebase adapter — works without touching the SPA.
factory-ui/src/ui/domains/auth/services/auth.ts:74, :103, :107
Exit gate
  • A CI test greps factory-ui/src for provider-name literals and fails on any hit.
  • MSW tests cover all four sign-in kinds, including an unrecognised provider.
  • Adding a new provider requires zero SPA changes — demonstrated, not asserted.
Phase 4

Conformance, providers, docs

~1 week

Where the work becomes durable. The conformance suite is what stops these grades sliding back the next time someone adds a provider.

Run conformance against every provider you ship
Expect failures — that is the point. Okta’s callback bug surfaces immediately, since its handleCallback has zero coverage today and that is exactly why the state mismatch went unnoticed.
auth/*/src/*.conformance.test.ts
Fix what conformance catches
Okta’s state lookup at minimum. Any provider you intend to support gets an ensureOrganization and a cookie-aware authenticateToken via the kit’s helpers.
auth/okta/src/auth-provider.ts:379, :412
Retire the 60-second boot tests
Move host provider-selection tests onto the factoryConfigs capture seam that already exists in the same file and is already used by another test there.
mastracode/web/src/mastra/index.test.ts:6–16, :315
Write the two documents that do not exist
A capability reference table, and a start-to-finish provider guide that ends with “now run the conformance suite.” Compile every example in CI so the guide cannot rot. Follow docs/AGENTS.md and the repo styleguides.
docs/ · mastracode/auth-kit/README.md
Exit gate
  • Every provider you ship passes conformance, or is explicitly marked unsupported with a reason.
  • Someone who has never seen this codebase writes a working provider from the guide alone. That is the actual test.
  • Doc examples type-check in CI.

Risks worth pricing in now

  • Phase 2 is the only phase that can break a live sign-in. Identity normalization, session cookies and logout all change together. Ship it behind a flag that falls back to the current sniffer for one release, and keep both paths covered until the flag comes out.
  • The kit re-exports from a package you do not control. @mastra/core/server could move a symbol or, worse, start barrelling EE the way @mastra/core/auth does. contract.ts exists precisely so that is a one-file fix — and the no-EE graph test would catch the bad case on the next dependency bump rather than in production.
  • “Reimplemented, not ported” needs to be visibly true. Write capabilities.ts from the interface definitions with the EE file closed. Different shape, different names, smaller scope. If it ends up looking like a paraphrase, that is a worse position than not having written it.
  • Providers you do not own can still fail the four obligations. Conformance proves the ones you ship; it cannot police a third-party package. The guide and the descriptor make failure legible early — that is the realistic ceiling.
  • Deploying to Mastra Cloud still rewraps your provider at build time, placing it last in a first-wins composite so its login URL is shadowed. Nothing in this plan changes that, because it lives in the deployer. Self-hosting is unaffected; know it before debugging a redirect that works locally and not in production.
