Architecture audit · mastracode/factory · auth layer

Two auth contracts wearing one name

Mastra’s provider contract is genuinely well designed — small structural interfaces, no base class required, publicly re-exported. But the Factory web app needs far more than that contract advertises, and only 2 of the 11 shipped providers can actually run it. Supabase and Firebase are not among them.

11 provider packages read 8 capability interfaces 5 seams audited every finding adversarially verified

The verdict, split two ways

The confusion in this codebase comes from one word doing two jobs. “Auth provider” means something small and well-specified when you are gating an API, and something large and unwritten when you are running the Factory SPA. Grade them separately and the picture is coherent.

Contract A — gate my API

A−

Two methods: authenticateToken and authorizeUser. Documented in a 519-line guide. Honored by all 11 providers. Structurally detected, so an out-of-tree package works. This part is genuinely plug-and-play.

Contract B — run the Factory

C

Roughly 20 methods across 6 interfaces, plus 4 obligations that appear in no interface at all. Documented in zero places — a grep of the entire docs tree for any of the six interface names returns nothing. Your goal lands here.

Seam Grade Why
Contract design B+ Eight small interfaces, purely structural guards, publicly exported, base class optional. Held back by authenticateToken returning unknown with no id requirement, and no cookie contract anywhere.
Backend seam B− Route derivation is capability-driven and the RouteAuth port is real dependency inversion — but identity is shape-sniffed, an org id is hard-required, and three modules bypass the port.
UI seam D+ The one decision that renders the sign-in screen is provider === 'better-auth' string equality. Everything beneath it is neutral and well built.
Testability B− fakeRouteAuth keeps 17 suites provider-free and the seam suite is a real executable spec. No conformance kit, and coverage is inverted — your drop-in targets have the thinnest tests.
Documentation D The docs that exist are good. They document Contract A. The capability surface a Factory provider must implement appears nowhere.

Both auth/supabase/src/index.ts and auth/firebase/src/index.ts define exactly two methods: authenticateToken and authorizeUser. They are Contract A packages. Nothing about them is broken — they were built to gate an API, and they do that well.

The four obligations no interface mentions

These are the ones that will cost you a debugging afternoon each, because nothing type-checks them and nothing documents them. A provider can satisfy every declared interface and still fail on all four.

A flat id, not uid or sub

The Factory re-sniffs whatever authenticateToken returns, and recognizes exactly two shapes: a {session, user} wrapper, or a flat object carrying id (or WorkOS’s workosId). Anything else authenticates as nobody.

mastracode/factory/src/auth.ts:190–231

Read the cookie yourself

The gate extracts a bearer token from Authorization and passes the raw Request as the second argument. Browsers send neither header nor bearer — so an empty token silently means “this is a navigation, go read the Cookie header.” That convention is written down nowhere.

mastracode/factory/src/auth.ts:787

Parse the pipe-delimited state

The Factory mints uuid|encodedReturnTo and hands handleCallback the raw value. packages/server splits it first and passes only the UUID. Two hosts, one interface, two incompatible contracts — this is precisely why the Okta provider’s callback can never succeed under the Factory.

auth.ts:434, :569  vs  handlers/auth.ts:443

Produce an organization id

Seven route groups 403 without one and the workspace layer throws outright. Either implement IOrganizationsProvider, or return organizationId directly on the user — the second route is undocumented but works.

factory.ts → routes/projects.ts:269, workspace.ts:316

Findings by seam

Each of these was written by one agent and then attacked by a second one whose job was to refute it. Severities below are post-refutation, not as first claimed.

Strength The contract layer is textbook interface segregation

IMastraAuthProvider requires two methods. Seven optional capability interfaces sit alongside it, and every runtime detection is a duck-typed typeof x.method === 'function' check — there is not a single instanceof in the guard set. The rationale is stated in the source itself.

provider/index.ts:34 — “Auth provider packages bundle their own copy of the MastraAuthProvider declaration, so provider class types cannot be compared nominally across package boundaries.”
packages/core/src/auth/index.ts:1 — export * from '@internal/auth'; — the whole surface is publicly re-exported
server.test-d.ts:122 — a compile-time regression test proving a nominally distinct duplicate class stays assignable
What this buys you An OIDC or Cognito provider can be a plain object with two methods plus whichever capabilities it wants, published from its own repo, with no base class and no monorepo membership. Someone fought for this and it holds.
High The SPA picks its sign-in screen by string equality on the provider name

/auth/me forwards only provider.name. The sign-in page compares it against two literals. A correctly-implemented Cognito provider signs in fine — the button navigates to /auth/login and the SSO flow works — but the button is labelled “Continue with GitHub” and wears a GitHub logo, because that is the fallback branch.

SignInPage.tsx:154–157 — const credentialForm = auth.data?.provider === 'better-auth'; / const studioAuth = auth.data?.provider === 'mastra-studio';
services/auth.ts:74 — the credentials form posts to /auth/api/sign-in/email, hardcoding better-auth’s wire format, not just its name
mastracode/factory/src/auth.ts:406–407 — the handler evaluates a capability guard one line before forwarding a bare name string
The sharpest detail in the audit Capability-driven sign-in UI already exists and ships. ee/capabilities.ts:285–315 builds exactly the descriptor the SPA needs, and docs/studio/auth.mdx:150 documents the resulting behavior as a feature. The Factory SPA just doesn’t call it. This is an unreused solution, not a missing one.
High An organization is mandatory, and CompositeAuth cannot supply one

Org-lessness 403s projects, work-items, audit, intake, knowledge and both integration route groups, and throws in the workspace layer. The obvious workaround — wrap any provider in CompositeAuth alongside a small local organizations provider — does not work, and it is worth knowing why before you try it.

provider/index.ts:169–171 — class CompositeAuth extends MastraAuthProvider implements ISSOProvider, ISessionProvider, IUserProvider
No ensureOrganization, no isOrganizationAdmin, no handleAuthRequest, no init anywhere in the class body
auth.ts:260 — if (!isOrganizationsProvider(provider)) return; — so the org bootstrap silently no-ops
Do this instead Implement ensureOrganization on the provider and mint a synthetic personal org. orgId is an opaque row-scoping string with no referential integrity anywhere — org:${userId} is a perfectly valid answer for Cognito, Supabase and Firebase, none of which have an organization primitive.
Medium Nobody owns the session cookie — three conventions and per-provider bespoke

No interface mentions cookies beyond opaque string[] returns. In practice there are three competing conventions: SimpleAuth’s mastra-token (hardcoded in the provider and re-read by regex in the host), a mastra_session default in two shipped session providers that no package uses, and one bespoke name per vendor (wos_session, Okta’s configurable name, Neon’s cookie plus a _sig sidecar, and so on).

packages/server/.../helpers.ts:461 — cookieHeader.match(/mastra-token=([^;]+)/) — the host reaching through to one provider’s cookie name by regex
mastracode/factory/src/auth.ts:281–282 — a regex that un-joins malformed clearing cookies, with the comment “A provider may join several clearing cookies into one header value”
session/cookie.ts:73 — a complete HMAC-signed CookieSessionProvider ships publicly and is used by zero providers
Why it matters for you When your new provider’s session doesn’t stick, there is no canonical place to look, because no layer owns the name. The already-shipped CookieSessionProvider is the fix nobody adopted.
Medium Logout diverges three ways, and the Factory never revokes a session

packages/server exposes POST /auth/logout and calls destroySession. The Factory exposes GET /auth/logout; on the SSO path it clears cookies and redirects, and on the http-handler path it POSTs to the provider’s own sign-out. A grep for destroySession across all of mastracode/ returns zero non-comment hits.

So for an SSO user, “log out” is a cookie deletion — a stolen token stays valid until natural expiry
A GET logout is CSRF-triggerable by any <img src="/auth/logout">
Five providers’ destroySession bodies are empty or comment-only — the method exists, the guarantee does not
packages/server also implements transparent session refresh; the Factory has no equivalent, so refreshSession works on /api/* and silently does nothing on Factory routes
Read this as Two hosts consuming one contract have drifted into three behaviors. That drift, not any single bug, is the maintainability risk.
Medium Deploying to Mastra Cloud rewraps your provider at build time

The Cloud deployer injects generated source into the built entry that replaces server.auth with a CompositeAuth — and places your provider last. Since CompositeAuth.getLoginUrl resolves via the first SSO provider, a Cognito provider deployed to Cloud has its login URL shadowed. RBAC is silently installed too.

deployers/cloud/src/utils/auth.ts:55–63 — const providers = [serviceAuth]; ... providers.push(userAuth); serverConfig.auth = new CompositeAuth(providers);
By contrast the bundler is clean: externals come purely from dependency analysis, and grepping the deployer and CLI for @mastra/auth returns nothing — a new provider package needs no build-system change at all
Scope Only affects Mastra Cloud deploys. Self-hosting is unaffected — but it is worth knowing before you debug a login redirect that works locally and not in production.
Medium No conformance kit, and coverage is inverted

The foundations are good: fakeRouteAuth is used by 17 suites, none of which stub an env var, and auth-seam.test.ts composes capability mixins onto bare object literals and asserts real HTTP responses. That is a genuine executable spec for the seam.

A grep for conformance|contract test|test-kit across auth/ and packages/_internals/auth/ returns nothing
Coverage runs backwards: auth/studio 1369 lines and auth/better-auth 1157, against auth/supabase 152 and auth/firebase 157
auth/okta has zero handleCallback coverage — which is exactly why its Factory-breaking state bug went unnoticed
No test drives a cookie-only request through the gate, though that is how every browser hits it
The cheapest high-value addition A shared conformance suite a provider can run against. It would have caught the Okta state bug, and it is the artifact that would turn “write a provider” from archaeology into a checklist.

What each target would actually take

Neither is a drop-in. Both are tractable, and they share most of the same work.

Generic OIDC & AWS Cognito

Meaningful work — new package

There is no OIDC or Cognito package today. auth/okta is the closest shape and gets four hard things right — configurable issuer, JWKS verification via jose, a flat string id mapped from sub, and cookie-first authentication — but it cannot complete a single Factory sign-in, because its callback looks up the state verbatim while the Factory passes the full pipe-delimited value. Fork the shape, fix the state contract, and Cognito becomes a preset.

  • Implement: the 2-method gate (cookie-first, flat id), ISSOProvider against the full state string, session-cookie minting via handleCallback’s cookies: [] return, getClearSessionHeaders, and ensureOrganization returning a synthetic org.
  • Skip: IAuthHttpHandler and IUserProvider — the Factory never calls them.
  • Blocked: PKCE. The write side (getLoginCookies) is declared and called; the read side is an undeclared hook that only packages/server invokes. Use a signed state or server-side verifier store instead.
  • Blocked: pure SAML. The interface is authorization-code shaped and the Factory registers /auth/callback as GET only, so a SAML POST binding has nowhere to land. Front it with an OIDC broker.

Supabase & Firebase

Meaningful work — extend existing packages

Both packages exist and both are bearer-validators. Supabase is the easier of the two: its user object already has a flat id, so the normalizer accepts it unchanged, and signInWithOAuth maps cleanly onto ISSOProvider. Firebase is harder for a structural reason — sign-in is client-SDK-driven, so the Admin SDK has no hosted-login URL to return.

  • Supabase: add ISSOProvider over signInWithOAuth, make authenticateToken cookie-aware, mint a session cookie, add ensureOrganization.
  • Firebase: go the IAuthHttpHandler route over the Identity Toolkit REST API instead of ISSOProvider. Also fix the user shape — DecodedIdToken exposes uid, and the Factory only accepts id, so today it would authenticate successfully and still be treated as anonymous at every ownership check.
  • Both: override authorizeUser. The shipped implementations check bespoke infrastructure (a Supabase users table, a Firestore user_access doc) and will 403 core /api/* without it.
  • Both: synthetic personal orgs. Neither vendor has an organization primitive — Firebase’s GCIP multi-tenancy is an isolation boundary, not a membership model.

What to fix, in order

Ordered by friction removed per unit of work. The first item is pure documentation and removes more friction than anything below it.

  1. Publish the capability contract
    A table mapping interface → routes unlocked → methods required, plus the four undocumented obligations. Zero code. Largest single reduction in friction.
  2. Put identity in the contract
    Require authenticateToken to return something with a string id, and drop workosId from the neutral FactoryAuthUser shape. The contract already defines a User with an id — it just declines to require it at the one place every host depends on it.
  3. Emit a capability descriptor from /auth/me
    Reuse the shape ee/capabilities.ts already builds, without its licence gate, and branch the sign-in page on that instead of a name string. Turns the UI seam from D+ into the same grade as the rest.
  4. Give the org requirement a host-side default
    A user:${userId} fallback already exists in the credentials path. Generalize it app-wide, since CompositeAuth provably cannot patch this from outside.
  5. Own the session cookie in the host
    Adopt the already-shipped CookieSessionProvider as the default and delete the mastra-token regex in the server helpers.
  6. Unify logout
    Call destroySession on the Factory’s SSO path, make it POST, and audit the five providers whose implementation is an empty body.
  7. Declare the PKCE read side
    Widen handleCallback to take the Request and delete the undeclared setCallbackCookieHeader hook. Unblocks @mastra/auth-cloud and any PKCE-based OIDC provider under the Factory.
  8. Ship a conformance kit
    A fake provider plus guard assertions a new package can run against. It would have caught the Okta state bug before it shipped.
Corrections the verification pass forced
  • The EE licence gate does not affect the Factory today. buildCapabilities ANDs SSO and credentials capabilities with a licence check whose only escapes are two first-party marker properties — but a grep confirms nothing under mastracode/ calls it. The effect is confined to Studio’s /auth/capabilities. It becomes a live trap only if you adopt fix 3 by reusing that builder with its gate.
  • The leftover WorkOS coupling is inert. The instanceof MastraAuthWorkos checks and the WORKOS_* env fallback in the neutral auth module sit on a code path with no production callers. Real cost: a vendor package as a hard dependency of the neutral module, and a forced vi.mock in both gate suites. Not a blocker for any drop-in.
  • Test coverage of org-less providers is better than first reported. A claim that no test covers a no-org provider was refuted — org-less gate behavior, the downstream 403, and the id-less-result-is-unauthenticated path are all pinned by existing tests.
  • The docs estate is not thin, it is aimed elsewhere. composite-auth, simple-auth, jwt, fga, workers and studio/auth all exist and are reasonable. The precise claim is that the six capability interfaces appear in zero docs files.
  • Per-tenant provider selection does not exist. One provider is resolved once at boot. CompositeAuth’s first-wins fallthrough is the wrong primitive for “each customer brings their own IdP” — that would need host- or tenant-keyed dispatch, which is not in the architecture today.
